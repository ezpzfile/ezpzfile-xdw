# XDW 실험 결과 (2026-10-01)

심판: **DocuWorks Viewer Light 10** (FUJIFILM 무료 뷰어). 클라우드의 Wine(일본어 환경)에서 자동 실행(`tools/dwview`).
코퍼스: 공개 파일 43개 (`corpus/manifest.tsv`, 세대 7·10, .xdw·.xbd).

## 1. 검사값(체크섬): 가장 중요한 발견

원본에서 1바이트씩 바꿔 뷰어로 열어 봄:

| 바꾼 곳 | 결과 | 뜻 |
|---|---|---|
| 마지막 트레일러의 0x85 | **거부** ("The file is not a DocuWorks document file.") | 이 값은 검사됨 |
| 항목(쪽)의 0x81 | 열림 | 항목 검사값은 열 때 검사 안 함 |
| 쪽 그림 데이터 | 열림 (그림만 깨짐) | 데이터 자체는 검사 안 함 |
| 속성 블록 | 거부 | 속성 블록이 0x85로 검사됨 |
| 이전 세그먼트의 트레일러·속성 | 열림 | 마지막 트레일러만 쓰임 |
| 트레일러 0x86(자기 길이) | 거부 | 파일 끝에서 트레일러를 찾는 데 씀 |
| 머리(0x60) | 거부 | |

계산법: 블록의 4바이트(리틀 엔디언) 단어를 모두 XOR. 코퍼스의 트레일러 26/26, 항목 463/463 일치.
속성을 우리 압축기로 다시 압축(크기·바이트가 원본과 다름) + 검사값 다시 계산 → **열림**.

## 2. DocuWorks 전용 그리기 기록 (DW…)

시험 그림을 넣은 쪽을 만들어 뷰어로 확인 (`tools/dwview`):

- `DW02` 경로 시작 / `DW03` 잘라내기 / `DW04` 채우기 / `DW05` 선 / `DW06` 사각 잘라내기
- 점 기록: 첫 점 i16, 이어서 i16·i8·니블(4비트) 걸음. 니블 8은 "다음 바이트에 걸음" (코퍼스 25,790개 기록에서 길이 정확히 맞음)
- op 비트: 0x01 새 도형, 0x02 닫기, 0x10 베지어, 0x20 단독 다각형(채우기), 0x40 단독 꺾은선
- 사진: `DWa` 기록 안 그림, `DWb` 쪽의 사진 목록에서 다음 것, `DWc` 그리기
- 옛 WMF 쪽의 `DW 02 00/01/02/03` (그림, 다음 사진, 그리기, 띠 채우기)

## 4. 화면 비교

코퍼스 43개 1쪽을 뷰어 화면과 우리 편집기 화면으로 나란히 비교 (`tools/webshot/compare.sh`).
글자·표·사진·지도·회전된 쪽·주석 모두 같은 모양. 차이는 글꼴(뷰어는 MS 글꼴, 우리는 기기 글꼴)과 부드러움 정도.

자동 테스트: `EZPZXDW_CORPUS=… cargo test`: 43개 전부 읽기, 모든 쪽 빠진 기록 없이 그리기, 속성 바이트 단위 왕복, 편집 후 저장·다시 읽기.

## 6. DocuWorks 10 정식판으로 확인 (2026-10-01)

**DocuWorks 최신판(10.1.1)** 을 클라우드 Wine에 설치.
DocuWorks Desk와 함께 설치되는 **DocuWorks API(xdwapi.dll)** 가 Wine에서 동작 → DocuWorks 엔진이 직접 파일을 읽고 그리게 함 (`tools/dwapi`).

| 시험 | 결과 |
|---|---|
| DocuWorks API로 日付印·付箋·글상자를 만들게 해서 저장 → 우리 도구로 속성 읽기 | 진짜 이름 확인: 日付印 `STAMPATT_POST/NAME/YEAR…`, 付箋 `FSN_COLOR` + 안에 글상자(자식). 우리가 추측한 이름(`%TopField` 등)은 API용 이름이었음 → 진짜 이름으로 고침 |
| 고친 뒤 우리가 만든 日付印·付箋을 DocuWorks API로 읽기 | 위 글자·아래 글자·날짜·색, 付箋 색·안의 글자까지 DocuWorks가 만든 것과 똑같이 읽힘 |
| 코퍼스 38개에 모든 편집(日付印·付箋·글상자·형광펜·사각형·타원·직선·그림·빈 쪽·사진 쪽·쪽 복사·회전, .xbd는 + 문서 추가·이름·순서) | **38/38**: 쪽 수·쪽별 주석 수가 우리 읽기와 일치, 첫 쪽·마지막 쪽 그리기 성공 |
| DocuWorks 10 샘플 5개(스캔·사진·설계도·계약서·바인더)에 같은 편집 | **5/5** 일치·그리기 성공 |
| 웹 편집기로 저장한 .xdw·.xbd | 2/2 일치, 日付印·付箋 속성 정확 |
| DocuWorks Desk 화면 | 우리 파일 4개가 목록에 쪽 수·썸네일(도장·付箋 보임)과 함께 표시. DocuWorks 10의 Viewer Light(빠른 보기)로 열림 |
| DocuWorks Viewer(편집용) | Wine에서 실행 중 오류로 꺼짐 (DocuWorks 파일과 무관, Wine 호환 문제로 보임) |

새로 알게 된 것:
- DocuWorks 10 스캔·사진 쪽은 그림 종류 **5 (JPEG 그대로)** → 우리 화면에 안 나오던 것을 고침
- DocuWorks 10 바인더는 문서 이름을 **70 (UTF-16)** 에 씀 → 읽기·이름 바꾸기 모두 지원
- 종류 0x8043 = **서명(電子印鑑)**. 편집하면 서명이 무효가 되므로 편집기에서 열 때 알려 주고, 서명은 옮기거나 지울 수 없게 함

## 7. v0.3: 글자 선택·찾기, 비치는 그림 (2026-10-02)

글자 선택·찾기는 웹 편집기에서 Playwright로 시험했다. 쪽의 글자를 끌어서 고르면 화면에 보이는 글자와 같은 글자가 복사되고, Ctrl+F로 일본어 낱말을 찾으면 찾은 곳으로 넘어가 그 글자가 골라진다.

비치는 그림은 먼저 그림을 어디에 담아야 DocuWorks가 비치게 그리는지 알아봤다. DocuWorks는 주석마다 저장된 그림(EMF)을 그대로 틀기 때문에, 그림을 SRCAND(곱하기)로 그리는 EMF를 넣으면 흰 부분으로 밑글씨가 보인다. 문제는 그 EMF를 담는 그릇이었다.

| 그릇 | DocuWorks에서 비침 | DocuWorks에서 옮기기 | DocuWorks에서 크기 바꾸기 |
|---|---|---|---|
| 그림 주석(0x803f) | 안 비침 (곱하기 무시) | 됨 | 됨 |
| 사각형 주석(0x803d)에 이 EMF | 비침 | 됨 | 사각형을 설정값으로 다시 그려서 **그림이 사라짐** |
| 사용자 지정 주석(0x8045), 모르는 `%annguid` | 비침 | API로는 됨. Viewer에서 **끌면 Viewer가 꺼짐** (`mpcstg.dll`이 주소 0에 씀) | API가 거부 |
| **붙여 넣은 그림(OLE 확장 메타파일, 0x800f)** | **비침** | **됨** | **됨, 꺼지지 않음** |

그래서 비치는 그림은 클립보드에서 붙여 넣은 그림과 같은 모양으로 저장한다. 공개 샘플(후쿠오카현 문서)에 DocuWorks가 만든 "Picture (Enhanced Metafile)" 개체가 있어서 그 구조를 따랐다. 개체 파일은 22바이트 머리 뒤에 OLE 복합 파일이 붙은 형태이고, 그 안의 `CONTENTS`는 머리 크기(108), 머리 사본, EMF 전체 순서다. 이 복합 파일을 쓰는 코드(`cfb.rs`)를 새로 만들었다.

| 시험 | 결과 |
|---|---|
| 우리 엔진으로 비치는 그림을 넣은 파일 → DocuWorks API 읽기·그리기 | 종류 32783(OLE)으로 읽힘, 흰 부분으로 밑글씨가 보임 |
| DocuWorks API로 옮기고 저장 → 다시 그리기 | 옮긴 자리에서 그대로 비침 |
| DocuWorks Viewer 화면에서 고르기·끌기·모서리로 크기 바꾸기·저장 | 꺼지지 않음. 고르면 기본 그림 주석처럼 손잡이 8개가 나옴. 저장한 파일에 우리 표시(`%ezpz_picture`)도 남아 있음 |
| Viewer에서 두 번 누르기 | "Failed to launch server application." 안내만 나옴 (붙여 넣은 그림은 원래 편집할 프로그램이 없음) |
| DocuWorks에서 크기를 바꾼 뒤 저장 | DocuWorks가 OLE에 다시 그려 달라고 하는데, Wine의 OLE는 이런 그림을 그리지 못해 빈 그림이 저장됨. DocuWorks가 만든 샘플 개체도 똑같아서 Wine 한계로 보임. Windows에서는 확인하지 못함 |
| 웹 편집기(Playwright): 투명 PNG 붙이기 → 크기 바꾸기 → JPEG 붙이기 → "白を透かす"로 바꾸기 → 저장 | PNG는 처음부터 비치는 그림으로, JPEG는 그림 주석으로 붙음. 바꾼 뒤 둘 다 OLE 개체. DocuWorks API로 그려도 편집기 화면과 같음 |
| 코퍼스 중 4 MB 이하 34개에 그림 주석·비치는 그림을 넣고 서로 바꾸기·크기 바꾸기 → 저장·다시 읽기 | 34/34 통과, 다시 읽은 그림의 화소가 넣은 것과 같음 |

우리 화면도 곱하기로 그리도록 고쳤다 (그림 항목에 `mul` 표시, 브라우저에서는 `multiply`). 전에는 SRCAND 그림의 흰색만 투명하게 처리했는데, 이제 색이 있는 부분도 밑글씨와 곱해져 DocuWorks와 같은 색이 나온다.

## 8. 서명 정보 읽기 (2026-10-02)

| 시험 | 결과 |
|---|---|
| DocuWorks 10 샘플 "契約書.xdw"(서명 2개) 읽기 | 두 서명 모두 종류(전자 도장)·모듈 `DocuWorks電子印鑑 (SHA1 V5以降)`·버전 `6.0`을 속성에서 그대로 읽음 |
| 웹 편집기에서 서명 고르기 | 속성 창에 종류·모듈·버전이 나오고, "편집하면 무효, 유효성 확인은 DocuWorks에서" 안내 표시 |
| 코퍼스 테스트에 서명 확인 추가 | 서명 개체가 있으면 모듈 이름이 비어 있지 않은지 검사 |

서명의 유효성(인증서가 지금도 믿을 만한지)은 DocuWorks API나 인증서 검증이 필요해서 아직 하지 않았다. 암호는 DocuWorks에 맡기기로 했다: 우리 엔진은 보호된 문서(항목 0x67, 속성 0x66)를 알아보고 "DocuWorks에서 보안을 푼 뒤 열라"고 안내만 하며, 암호는 다루지 않는다. DocuWorks API로 만든 보호 샘플 3종(128비트 둘, 256비트) 모두 "보호된 문서"로 알아봤고, 웹 편집기에서도 안내 창이 뜬다.
